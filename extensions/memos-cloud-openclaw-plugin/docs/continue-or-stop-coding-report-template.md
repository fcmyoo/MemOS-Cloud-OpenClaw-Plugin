## 3. 判定规则

### 3.1 直接判定为“继续改代码”

同时满足以下条件时，可判定为 `继续改代码`：

- 20 条查询验证中，`通过` 不少于 16 条，且失败项不存在同一根因大面积重复。
- 8 轮对话验证中，`通过` 不少于 6 轮，且至少 4 轮能稳定体现目标能力。
- 不存在 P0 / P1 级阻断问题；即使存在缺陷，也已明确到可执行的修复点。
- 继续开发的改动方向清楚，下一轮能聚焦到少量具体问题，而不是重新定义目标。
- 继续开发的预期收益高于排查成本，且没有更低成本的替代方案明显优先。

### 3.2 判定为“暂停改代码”

满足任一条件时，优先判定为 `暂停改代码`：

- 查询验证或对话验证结果处于中间态，现有证据不足以下继续/停止结论。
- 问题根因尚未收敛，失败现象分散，继续写代码大概率只会扩大试错成本。
- 当前更适合补日志、补观测、补样本、补测试基线，而不是直接动业务逻辑。
- 当前收益判断依赖更多真实样本，现有 20 条查询或 8 轮对话代表性不足。

### 3.3 直接判定为“停止改代码”

满足任一条件时，应判定为 `停止改代码`：

- 20 条查询验证中，`失败` 超过 8 条，或核心场景失败超过 4 条。
- 8 轮对话验证中，`失败` 超过 3 轮，或连续 3 轮无法体现目标能力。
- 已确认主要问题不在代码，而在需求错误、评价口径错误、数据源不足、接口能力上限或外部约束。
- 即使继续投入开发，也看不到清晰的收益路径，或改动成本明显高于价值。
- 同类失败集中指向架构级问题，短期修补无法形成可信改善闭环。

### 3.4 覆盖性约束

以下任一情况成立时，不得轻易给出 `继续改代码`：

- 查询验证只在容易样本上通过，缺少边界样本、反例样本、噪声样本。
- 对话验证只看单轮效果，没有覆盖多轮记忆、上下文切换、追问、纠错等场景。
- 验证记录缺少原始输入、输出摘要、失败原因，导致结论不可复核。
- 本轮成功主要依赖人工解释或临时补救，而非系统稳定表现。

## 10. 附录

### 10.1 填写说明

- `通过`：达到预期，且结果可稳定复现。
- `部分通过`：部分达到预期，但仍有明显缺口或不稳定因素。
- `失败`：未达到预期，或虽然有结果但方向错误/副作用不可接受。
- `核心场景`：直接影响是否值得继续投入开发的关键用户场景。
- `一票否决项`：即使总体通过数尚可，只要命中就不能贸然继续改代码的问题，例如核心场景持续失败、外部约束不可解、收益明显不成立等。

### 10.2 推荐根因分类口径

- 查询词问题
- 样本覆盖不足
- 召回不到
- 召回到了但排序不对
- 归一化丢信息
- Prompt 注入后未被模型有效利用
- 对话链路中记忆污染或串话
- 外部接口返回受限
- 不是代码问题，而是目标定义错误
