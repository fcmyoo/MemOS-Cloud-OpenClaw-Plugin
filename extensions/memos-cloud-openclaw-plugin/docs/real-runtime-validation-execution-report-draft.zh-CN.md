## 2. 本轮验证目标

本轮不是继续猜测插件“理论上能不能用”，而是要在真实运行态下确认以下 4 件事：

1. 插件在真实会话链路里，是否真的会在 `before_agent_start` 做召回、在 `agent_end` 做写回。
2. 20 条更接近真实用户表达的查询，是否能稳定验证召回、过滤、知识库范围、会话隔离、噪声抑制和高风险约束优先级。
3. 8 轮连续对话里，偏好、事实、混合记忆、回退链路、降级链路是否在真实日志中可观察、在用户侧可感知。
4. 现阶段是否已经达到“值得继续改代码”的证据门槛，还是应该先暂停改代码、补观测或补样本。

## 3. 现在就能确认的静态结论

以下结论无需等待真实运行，可直接依据仓库现状确认：

### 3.1 已落地的验证材料

仓库内已经具备 3 份可复用模板：

- `validation/real-query-validation-checklist.md`：定义了 20 条真实查询、执行前准备、检查项和通过口径。
- `validation/real-query-validation-set.json`：提供同一批 20 条查询的结构化数据版本。
- `docs/8-round-manual-dialog-checklist.zh-CN.md`：定义了 8 轮真实对话验证的逐轮目标、输入、通过标准和失败标准。
- `docs/continue-or-stop-coding-report-template.md`：定义了验证完成后如何判断 `继续改代码 / 暂停改代码 / 停止改代码`。

### 3.2 插件链路与日志事件已具备观测点

从 `index.js` 与 `lib/memos-cloud-api.js` 可确认：

- 召回发生在 `before_agent_start`。
- 写回发生在 `agent_end`。
- 召回成功事件为 `recall.success`。
- 召回失败事件为 `recall.failed`。
- 写回成功事件为 `add.success`。
- 写回失败事件为 `add.failed`。
- 若启用 LanceDB，本地召回事件可观察 `lancedb.recall`。
- 若触发 MemOS 召回，可观察 `memos.recall` 及 fallback 字段。
- 失败时是否阻断主流程，取决于 `memoryDegradeOnError`。

### 3.3 查询请求的关键参数口径已明确

从代码可确认真实查询时重点要核对这些 payload 字段：

- `user_id`
- `session_id`
- `query`
- `readable_cube_ids`
- `top_k`
- `include_preference`
- `pref_top_k`
- `search_tool_memory`
- `tool_mem_top_k`
- `relativity`
- `filter`
- `source`

### 3.4 写回请求的关键参数口径已明确

真实运行态要核对写回 payload 至少包含：

- `user_id`
- `session_id`
- `messages`
- `async_mode`
- `source`
- `info.scope_key`
- `info.chat_id`
- `info.user_id`
- `info.scope_mode`

### 3.5 默认行为已可静态判断

从配置构建逻辑可确认：

- `recallEnabled` 默认开启。
- `addEnabled` 默认开启。
- `captureStrategy` 默认是 `last_turn`。
- `includePreference` 默认开启。
- `includeToolMemory` 默认关闭，需显式开启。
- `recallGlobal` 默认是 `true`。
- `memoryDegradeOnError` 默认是 `true`。
- `knowledgebaseIds` 默认空数组，不配置就无法验证知识库过滤。

## 4. 必须等待真实运行态才能确认的结论

以下内容现在不能凭代码阅读直接下结论，必须等真实执行结果：

- 20 条查询中到底有多少条 `通过 / 部分通过 / 失败`。
- 高风险约束类查询是否真的稳定排在前面，而不是只在静态设计上成立。
- 负样本和噪声查询是否真的被抑制，没有误召回。
- 会话隔离在真实 session A/B 下是否真的不串数据。
- `knowledgebaseIds` 过滤在真实数据集里是否真的只返回目标知识库。
- 8 轮对话里，多条偏好和事实混合召回是否足够稳定。
- LanceDB 弱命中或空命中时，fallback 到 MemOS 的行为是否与日志一致。
- 异常场景下的降级是否真正不阻断主对话。
- 是否达到继续改代码的判定门槛。

## 5. 真实运行态环境前提

以下前提建议在执行前逐项打勾，任何缺项都可能导致验证结果失真。

### 5.1 插件与服务前提

- [ ] 插件已启用：`plugins.entries.memos-cloud-openclaw-plugin.enabled = true`
- [ ] OpenClaw gateway 已重启，确保最新配置生效
- [ ] `MEMOS_API_KEY` 或插件 `config.apiKey` 已配置
- [ ] MemOS Cloud 服务当前可访问
- [ ] 若验证本地精排召回，LanceDB 参数已配置且 embedding key 可用
- [ ] 如需验证 fallback，`memosSearchFallbackEnabled` 已按计划配置
- [ ] 如需验证降级，`memoryDegradeOnError` 已明确当前取值

### 5.2 数据样本前提

- [ ] 已准备一组可控记忆样本，至少覆盖：偏好 / 决策 / 事实 / 故障 / 工具记忆 / 负样本
- [ ] 如需验证知识库过滤，至少准备 2 个不同 `knowledgebaseIds`
- [ ] 如需验证会话隔离，至少准备 A/B 两个独立 session
- [ ] 如需验证 recallGlobal 差异，已规划 `true / false` 两组对照

### 5.3 执行与观测前提

- [ ] 有固定测试用户，避免与真实生产会话混淆
- [ ] 有可查看网关日志的终端
- [ ] 有可记录每条查询结果的表格或文档
- [ ] 已记录当前分支、提交号、环境标识、时间窗口
- [ ] 如走远端服务，网络延迟与超时在可接受范围内

## 6. 日志观察点

真实运行态建议按“请求发出 -> 召回结果 -> 注入上下文 -> 写回结果 -> 异常降级”顺序观察。

### 6.1 召回阶段必看日志

- `before_agent_start` 是否触发
- `lancedb.recall` 是否出现，返回数量和耗时是否合理
- `memos.recall` 是否出现
- `recall.success` 是否出现
- `recall.failed` 是否出现
- `recall.gray_skip` 是否意外出现

### 6.2 召回阶段要核对的字段

- `trace_id`
- `cost_ms` / `elapsed_ms`
- `lancedb_count`
- `memos_success`
- `recall.lancedb.count`
- `recall.lancedb.top_score`
- `recall.fallback.enabled`
- `recall.fallback.should_fallback`
- `recall.fallback.reason`
- `recall.memos.summary`
- `recall.unified.count`
- `total_chars`

### 6.3 写回阶段必看日志

- `agent_end` 是否触发
- `add.success` 是否出现
- `add.failed` 是否出现
- `message_count` 是否符合 `captureStrategy` 预期
- `scope_key` / `session_id` 是否稳定

### 6.4 异常与降级阶段必看日志

- 错误出现时是否有 `degrade: true`
- recall 失败后主对话是否继续返回答案
- add 失败后是否仅影响记忆写回而不影响用户回答
- 是否出现缺 API Key、401、网络错误、超时等基础设施问题

## 7. 真实运行态执行步骤

建议按以下固定顺序执行，避免变量混杂导致结论不可复核。

### 第 1 步：锁定验证环境

- 记录当前分支、提交号、插件配置摘要、测试时间、测试入口。
- 明确本轮是否启用 LanceDB、本轮是否启用 fallback、本轮是否验证 knowledgebaseIds、本轮是否验证 A/B session。

### 第 2 步：确认基础连通性

- 启动或重启 OpenClaw gateway。
- 确认插件已加载。
- 确认 MemOS Cloud 可访问。
- 如启用 LanceDB，确认本地召回链路可用。

### 第 3 步：打开日志观察终端

- 保证能连续观察 `recall.success`、`recall.failed`、`add.success`、`add.failed`。
- 若可行，同时记录每轮请求对应的 `trace_id`。

### 第 4 步：执行 20 条真实查询验证

- 严格按本报告第 8 节顺序逐条执行。
- 每条只验证一个主要目标。
- 每条执行后立即记录状态、命中记忆、误召回、是否跨会话泄漏。

### 第 5 步：执行 8 轮连续对话验证

- 在同一测试会话中按本报告第 9 节顺序执行。
- 不在中途切换用户，不插入无关额外轮次。
- 逐轮核对日志与用户可见回复是否一致。

### 第 6 步：执行异常与降级验证

- 在测试环境下制造可控异常，例如 API Key 错误、服务不可达或超时。
- 验证 `memoryDegradeOnError` 生效时，主对话是否仍可用。

### 第 7 步：填写结论模板

- 将查询结果与对话结果回填到 `continue-or-stop-coding-report-template.md` 对应结构。
- 依据模板中的门槛，给出 `继续改代码 / 暂停改代码 / 停止改代码`。

## 10. 判定口径

真实运行结束后，结论建议直接套用仓库模板中的判定规则。

### 10.1 可判定为“继续改代码”

同时满足以下条件时，可给出正向结论：

- 20 条查询验证中，`通过` 不少于 16 条。
- 8 轮对话验证中，`通过` 不少于 6 轮。
- 没有 P0 / P1 级阻断问题。
- 失败项根因已收敛到少量具体修复点。
- 下一轮开发目标清楚，不需要重新定义问题。

### 10.2 应判定为“暂停改代码”

满足以下任一情况时，更合理的动作是先补验证而不是写代码：

- 查询或对话结果处于中间态，证据不足。
- 问题根因分散，暂时看不出主因。
- 当前更需要补日志、补样本、补基线。
- 真实样本代表性不足。

### 10.3 应判定为“停止改代码”

满足以下任一情况时，不应继续加码开发：

- 20 条查询中失败超过 8 条，或核心场景失败超过 4 条。
- 8 轮对话中失败超过 3 轮，或连续 3 轮无法体现目标能力。
- 已确认主要问题不在代码，而在需求、数据源或外部能力上限。
- 即使继续投入，也没有清晰收益路径。
